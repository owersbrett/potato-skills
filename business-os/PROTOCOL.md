# PROTOCOL.md — the Business OS module contract

The shared contract every stone in the `business-os` family obeys. A **stone**
is one canonical business document, composed by its skill, shipped as a
**module**: a standalone website + data layer + MCP surface that runs alone
today and snaps into the master intranet the day the other stones exist.

Read this before composing any stone and before assembling the master site.

## The design thesis

1. **Standalone value.** Every module earns its keep alone: its own
   `npm run dev`, its own document site, its own tables the owner can start
   filling on day one. No stone waits for another to be useful.
2. **The ghost town.** The *integrated* system is deliberately bigger than one
   person. The master intranet renders every room of the business — including
   the empty ones. Empty tables show their empty states honestly; missing
   stones appear as boarded-up rooms with a note about who would live there.
   The system working correctly should make a non-technical owner feel the
   shape of the company they haven't hired yet — and go find a technical
   founder. Emptiness is the onboarding funnel. Never fake occupancy.
3. **Documents are the API.** Agents and humans coordinate through the
   canonical documents. Machine-readable contracts exist so software can
   consume them; CLAUDE.md files exist so future agent sessions update them
   correctly instead of drifting.

## Workspace layout

All stones for one business live in one workspace:

```
<business>/
  CLAUDE.md              ← root: doc map, update protocol, SSOT rules
  vision/
    module.json          ← the manifest (schema below)
    CLAUDE.md            ← how to update THIS document, and what breaks downstream
    VISION.md            ← the canonical document (SSOT)
    vision.json          ← machine-readable contract
    db/schema.sql        ← core tables
    db/seed.sql          ← empty-state-honest seed (labels, not fake rows)
    mcp/                 ← MCP server exposing doc + tables
    site/                ← the standalone website (own package.json)
  customer-blueprint/
  …
  intranet/              ← generated by the master skill, last
```

## module.json — the manifest

Every module ships one at its root. This is what the master skill scans for.

```json
{
  "protocol": "business-os/1",
  "slug": "vision",
  "title": "Vision & Positioning",
  "layer": "purpose",
  "order": 1,
  "doc": "VISION.md",
  "contract": "vision.json",
  "db": { "schema": "db/schema.sql", "seed": "db/seed.sql", "file": "db/vision.sqlite" },
  "mcp": "mcp/server.mjs",
  "site": {
    "dir": "site",
    "devPort": 4001,
    "dev": "npm run dev",
    "build": "npm run build",
    "dist": "site/dist",
    "basePath": "/vision/"
  },
  "upstream": [],
  "status": { "locked": ["…section ids…"], "placeholder": ["…section ids…"] }
}
```

Rules:

- `protocol` is versioned; the master refuses manifests it doesn't speak.
- **Ports:** master takes `4000`; stones take `4001`–`4008` by `order`. At
  compose time, verify the port is actually free before hardcoding it into the
  module's package.json; if taken, walk upward and record the final value in
  `module.json` — the manifest, not convention, is what the master reads.
- **`basePath`:** the site must build static under a configurable base
  (`/[slug]/`) so the master can mount it under one domain. Standalone builds
  use `/`.
- `status` is maintained by the stone's skill on every update — the master's
  coherence dashboard reads it.

## The document pair: `<DOC>.md` + `<slug>.json`

- The **Markdown document** is the canonical, human-owned SSOT — section-per-
  section, every locked decision, loud `PLACEHOLDER` markers for unknowns.
- The **JSON contract** is the machine-readable projection: the values other
  software consumes (brand → tokens; customer → personas; business-model →
  pricing table). Every fact in the JSON exists in the Markdown; the JSON
  never says more than the document.
- Composition follows **propose → confirm → lock** (see any stone's SKILL.md).
  A fact lives in exactly one stone; downstream stones cite, never restate.

## Data layer — core tables, day one

Each stone ships SQLite (`db/<slug>.sqlite` from `schema.sql`) — zero-infra,
file-based, attachable by the master. The tables are the stone's *operational*
half: where the living data goes once the document says what should exist.
Examples of the standard each stone must meet: customer-blueprint ships
`personas` and `interviews`; go-to-market ships `leads` and `campaigns`;
operations ships `decisions` and `meetings`. Seeds create structure and
empty-state copy only — **never sample rows pretending to be a business**.

## MCP — the out-of-the-box agent surface

Each module ships a small MCP server (`mcp/server.mjs`, stdio) exposing four
standard tools, namespaced by slug:

| Tool | Does |
|---|---|
| `<slug>_get_document` | Returns the canonical Markdown (whole or by section). |
| `<slug>_get_contract` | Returns the JSON contract. |
| `<slug>_query` | Read-only SQL over the module's tables. |
| `<slug>_record` | Insert into a core table (the write path for operational data). |

**Document edits are not an MCP tool.** Updating the canonical document goes
through an agent session under the module's CLAUDE.md (below) — taste stays
human-approved. The module also ships the `.mcp.json` snippet to register its
server with Claude Code / Claude Desktop, so "out of the box" means paste one
block.

## CLAUDE.md — the update protocol

The system is set up so *future agent sessions* maintain it correctly:

- **Root `CLAUDE.md`** (workspace): names the business, maps every stone
  (slug → document → what reads it), and states the laws: documents are SSOT;
  one fact one home; propose → confirm → lock; placeholders over
  fabrications; after any doc change, update the JSON contract, `status` in
  `module.json`, and check downstream stones for now-stale citations.
- **Per-module `CLAUDE.md`**: how to update *this* document — which skill to
  re-invoke for a structured revision, which sections are load-bearing for
  which downstream stones, the module's own do-not list.

## The master intranet (`intranet`)

Composed last, by its own skill. It:

1. Scans the workspace for `module.json` manifests (any subset — partial
   assembly is the normal case, and the point).
2. Builds each present module's site under its `basePath` and mounts them in
   one shell: unified nav (all eight rooms, present or not), cross-document
   links, per-stone status from the manifests.
3. Renders the **ghost town**: absent stones and empty tables as honest,
   designed emptiness — each empty room names the role/hire/agent that would
   fill it.
4. Runs the **coherence dashboard**: placeholder counts, stale-downstream
   warnings, contradiction flags across documents.
5. Hosts the **advisor** — the one live (non-static) component: a small
   server route that loads every canonical document as context and makes
   grounded recommendations: infrastructure provisioning, hiring order,
   agent/automation use cases, Claude Code admin setup, network
   considerations, and events worth networking at. The advisor cites which
   document grounds each recommendation; where documents are silent it says
   so — same placeholder ethic, spoken aloud.

## Definition of done — any stone

1. Canonical document written, every rubric section present or explicitly cut.
2. JSON contract matches the document exactly.
3. `schema.sql` creates the core tables; seed is empty-state honest.
4. MCP server runs and all four tools answer.
5. Site runs standalone (`npm run dev`, its declared port) and builds under a
   base path.
6. `module.json` validates against this protocol; `status` is truthful.
7. Module `CLAUDE.md` written; root `CLAUDE.md` created or updated.
